# Расширенный статус сервиса

На вкладке **«Сервис»** кнопка **«Прочитать расширенный статус…»** получает
читающий снимок с авторизацией через установленный root-помощник. Предварительно
читать конфиг не требуется. GUI работает обычным пользователем; код из checkout
не повышается до root. На рабочей системе при разработке помощник не обновлялся
и административная проверка не запускалась.

## Что показывается

- systemd: LoadState, ActiveState, SubState, MainPID, Result, ExecMainStatus;
- свежий профиль и настроенный backend из конфига, либо отдельная ошибка;
- путь, размер в данных отчёта и SHA-256 установленного файла nfqws;
- PID nfqws текущего релиза в cgroup именно управляемого systemd-сервиса;
- фактическая очередь из аргумента `--qnum`, ожидаемая очередь приложения 220;
- именованная таблица nftables и распознанные queue-правила;
- цепочки IPv4/IPv6 iptables и распознанные NFQUEUE-правила;
- отдельные предупреждения и ошибки чтения.

Версия nfqws не угадывается и не извлекается запуском бинарника. Показанный
профиль — **профиль в конфиге**, не доказательство того, что работающий процесс
запущен именно с ним: конфиг мог измениться после запуска. SHA-256 относится
к установленному файлу движка. Backend `auto` не подменяется предположением
на основе наличия команды: наблюдения правил двух backend показаны отдельно.

Это снимок с временем, не непрерывный мониторинг. После изменений его нужно
прочитать заново. Локальные сервисные/административные изменения через backend
сбрасывают сохранённый снимок. Базовое состояние systemd перечитывается отдельно;
отказ доступа, запуск/остановка, failed и неуправляемый одноимённый unit не
выдаются за успешно остановленный или отсутствующий сервис.

## Границы чтения и доверия

Новый протокол `read-status` принимает **только `{}`**, без путей, PID или
команд пользователя. Capability — `service-status-v1`; для независимой от
чтения конфига проверки поддержки GUI читает маркер
`# read-only-service-status-v1:` в уже проверенном установленном помощнике.
Старый помощник не получает неизвестную операцию: кнопка отключена с объяснением.

После проверки управляемой установки помощник использует её доверенный
`src/lib/service_status.py`. Ни конфиг, ни shell-файлы не исполняются.
Повреждённый конфиг не блокирует остальные наблюдения и не исправляется.
Чтение выполняется под существующей блокировкой установщика; конфиг, данные,
код, состояние сервиса, hosts, sysctl и правила не переписываются.

Используются только фиксированные команды чтения:

```text
systemctl show zapret_discord_youtube.service --property=…
nft -j list tables
nft -j list table inet zapretunix
iptables -t mangle -S
ip6tables -t mangle -S
```

Нет shell, `start/stop`, `flush/delete`, `pkill`, сетевых HTTP/DNS-проб или
запуска движка. У команд таймаут 12 секунд; ответы и читаемые файлы ограничены
по размеру. Полный чужой ruleset и полные argv процессов в GUI не выводятся.

Процессы берутся из `cgroup.procs` cgroup v2 unit. Для каждого PID проверяются
`/proc/<pid>/cgroup`, ссылка exe на nfqws текущего релиза и очередь; повторно
проверяются exe и членство. Глобальный поиск `pgrep nfqws` не используется:
одинаковое имя процесса или бинарника вне cgroup не доказывает владения.
Исчезновение процесса, гонка, недоступный procfs/cgroup и неподдерживаемая
структура дают **«неизвестно»**, а не ложное «процессов нет». Снимок не атомарен
относительно внешних системных изменений. cgroup v1 и процессы во вложенных
пользовательских cgroup этим механизмом полноценно не покрыты.

Отсутствие nft-таблицы устанавливается только после успешного перечисления
таблиц. Ошибка доступа, отсутствующий инструмент, плохой JSON и timeout —
**неизвестно**, не отсутствие правил. Для nft распознаются таблица `inet
zapretunix`, цепочки `pre/post`, комментарий `Added by zapret script` и queue.
Для iptables — цепочки `zapret/reply`, connbytes и NFQUEUE с bypass, отдельно
читаются IPv4/IPv6. Имена/сигнатуры не являются криптографическим доказательством
принадлежности и не используются здесь для удаления ресурсов. Таблица без
распознанных правил и различающиеся очереди дают предупреждения.

Наличие процесса и правил не доказывает работоспособность DPI-обхода, видео,
QUIC или голоса. Ошибок не обнаружено — не равнозначно «всё исправно».

## Проверки 12 ноября 2026

**22 офлайн-теста** в `ci/test_service_status.py`: cgroup и exe, исключение
постороннего процесса, ошибка чтения/смена членства, остановленный unit,
небезопасный путь cgroup, распознавание nft/iptables, недостаточность одного
имени таблицы, отказы доступа, отсутствие инструментов/таблицы, плохой JSON,
несовпадение очередей, фиксированные команды, timeout systemd, пустой протокол,
деморежим, старый помощник, базовый неизвестный статус и тексты состояний.

Всего **264 теста OK**. GTK demo smoke — **24 операции PASS**, включая
чтение снимка активного и остановленного сервиса. Подтверждения мышью и
интерактивная авторизация не имитируются.

### Отмеченная VM

`ci/vm_service_status_smoke.py`: **39 PASS** в Ubuntu 24.04/KVM, ядро
`6.8.0-147-generic`. Настоящий nfqws, установленный изолированный помощник,
стратегия ALT12, queue 220. Проверены остановленный/работающий сервис,
SHA-256 движка, точное множество PID текущего релиза, три queue-правила
nftables и шесть правил IPv4/IPv6 iptables. Совместимые таблицы iptables-nft
не принимаются за таблицу собственного nftables-backend.

Обычный пользователь получает `unknown` при реальном отказе kernel читать
правила. Временно повреждённый конфиг даёт ошибку конфига при сохранении
наблюдений процесса и правил. Проверены неизменность файлов кода/данных,
MainPID и структуры ruleset, сохранение посторонних nfqws и nft-таблицы.

Первое расширение VM-сценария на iptables выявило ошибку проверки: сравнивались
живые счётчики. Diff подтвердил изменение только `counter packets/bytes` от
обычного трафика. Финальный прогон сравнивает `nft --stateless list ruleset`:
структура правил и PID по-прежнему должны совпадать, счётчики не замораживаются.

Установка и sentinel-ресурсы удалены. Пустые совместимые таблицы `ip/ip6 mangle`
после iptables не удаляются приложением как потенциально общие ресурсы; после
сценария в отмеченном госте они дополнительно удалены тестовым cleanup только
после проверки отсутствия любых правил и наличия одних пустых ACCEPT-цепочек.
Итог: unit not-found/inactive, nfqws нет, ruleset пуст, VM выключена.

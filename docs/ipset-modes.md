# Режимы IPSet в GUI

На вкладке **«Настройки»**, после явного чтения конфига, доступен выбор:

- **loaded** — использовать сохранённый непустой набор IP/CIDR;
- **none** — использовать заглушку `203.0.113.113/32`, как в Flowseal;
- **any** — использовать пустой IPSet, то есть не ограничивать основной фильтр
  стратегии адресами из загруженного набора.

Это не глобальный переключатель всего firewall: режим затрагивает только
`--ipset=…ipset-all.txt` в выбранной стратегии. Списки доменов, пользовательские
исключения, другие IPSet-файлы и отдельные Game Filter-профили не переписываются.
Для стратегии без такого основного IPSet режим сам по себе ничего не расширяет.

Изменение в списке не применяется автоматически. Кнопка **«Применить режим
IPSet…»** показывает подтверждение; может потребоваться авторизация. Работающий
сервис перезапускается, остановленный не запускается. Повтор идентичных настроек
не вызывает перезапуск. В случае неудачного запуска восстанавливаются конфиг и
предыдущая работа сервиса; сбой восстановления показывается отдельно.

## Хранение без перезаписи списков

В конфиг добавлен необязательный ключ:

```ini
ipset_mode=loaded
```

Если ключа нет, используется совместимое поведение **legacy**: старый основной
файл и его пользовательское переопределение работают как прежде. В GUI режим
определяется по содержимому, а не предполагается равным loaded. Пустой список
означает any; набор только из заглушки — none. Повреждённые и отсутствующие
данные показываются как неизвестные/недоступные, а не как успешная загрузка.

При явном выборе none/any runtime подставляет защищённый встроенный файл из
`src/lib/ipset-none.txt` или `src/lib/ipset-any.txt`. Его содержимое проверяется.
Ни upstream-файл, ни пользовательский основной набор для переключения режимов
не очищаются и не заменяются. Это поддерживают оба runtime: legacy Bash и
скомпилированный каталог. Включения и исключения различаются: `--ipset-exclude`
не меняется при подстановке основного списка.

Для loaded выбирается первый существующий валидный непустой набор, не являющийся
заглушкой, в следующем порядке:

1. Постоянный `user-lists/ipset-all.txt`.
2. Постоянный `user-lists/ipset-loaded.txt`.
3. Постоянный legacy `user-lists/ipset-all.txt.backup`.
4. Текущий upstream `zapret-latest/lists/ipset-all.txt`.
5. Его legacy `ipset-all.txt.backup`.

Пустые файлы и заглушки пропускаются. Повреждённый существующий кандидат не
заменяется молча другим набором. В GUI показываются путь, число записей и SHA-256
выбранных данных. Если подходящего набора нет, loaded недоступен; none/any остаются
явными вариантами восстановления. Отдельное скачивание нового IPSet реализовано
кнопкой «Обновить список IPSet…»: оно заменяет основной постоянный набор, не
меняя выбранный режим и исключения; подробности и границы проверки —
[обновление IPSet](ipset-update.md).

При первоначальной установке/обновлении из подготовленного checkout валидный
`user-lists/ipset-all.txt.backup` переносится **в приватной копии пакета** в
`ipset-loaded.txt`, если такого сохранённого файла ещё нет. Исходный backup не
трогается. Существующие постоянные пользовательские файлы установщик не
перезаписывает. Другие `.backup` не устанавливаются как рабочие списки.

## Проверки и границы полномочий

- Разрешены только буквальные IPv4/IPv6 и числовые CIDR-префиксы; поддерживаются
  пустые строки, обычные комментарии, UTF-8 BOM и CRLF. Shell-текст, scoped IPv6,
  недопустимые префиксы и необычные разделители строк отклоняются.
- Файл должен быть обычным, без следования symlink; FIFO не блокирует проверку.
  Ограничения: 8 MiB и 200000 записей.
- Помощник принимает только режим, SHA-256 конфига и, для loaded, SHA-256 набора.
  Произвольный путь/команда/unit через запрос не принимаются.
- Содержимое списка проверяется до остановки сервиса. Если оно изменилось после
  просмотра, требуется перечитать настройки; правки другого процесса не
  перезаписываются при отказе.
- Чтение структурно корректного конфига возможно и при пропавшем loaded-наборе:
  так пользователь может явно выбрать none/any из GUI. Применение кандидатов и
  проверка перед переключением релиза остаются строгими.
- Нужен runtime с маркером `# ipset mode v1`. Старый helper без capability
  `ipset-mode-v1` не получает неподдерживаемые запросы: новые элементы GUI
  отключаются с объяснением. Обновление установленной копии не выполняется скрыто.

## Проверка 11 ноября 2026

- **144 офлайн-теста проекта**, включая 19 тестов IPSet и проверку GUI-протокола.
- GTK demo smoke: **13 операций**, включая три режима IPSet, Game Filter,
  старый helper и подробности ошибки. DemoBackend не обращается к системе.
- **6 настоящих nfqws dry-run** для локальной ALT12: loaded/none/any для обоих
  runtime. На рабочей системе сервис, демон, списки и firewall не менялись.
- Новая одноразовая KVM VM: Ubuntu 24.04 x86_64, kernel `6.8.0-147-generic`,
  nftables, nfqws v72.9. `ci/vm_ipset_smoke.py` прошёл **192 утверждения**;
  в число включены повторные проверки состояния и сохранности ресурсов.

В VM проверены 12 сочетаний: три режима × active/inactive × legacy/compiled.
Проверялся не только конфиг, но и фактический `--ipset` в `/proc/.../cmdline`
настоящего nfqws и сохранение `--ipset-exclude` на постоянный пользовательский
файл. Байты всех списков и установленного релиза при переключениях не менялись.
Сохранённый loaded-набор остался доступен после синхронизации стратегий.

Также проверены no-op, неверный режим, устаревшие токены конфига и списка,
отсутствие остановки при отказе, сохранность другого nfqws на очереди 221 и
посторонней nftables-таблицы. Дважды намеренно вызван одноразовый start failure:
предыдущий конфиг и работа сервиса восстановились, списки сохранились.

Синхронизированный каталог в прогоне получен из публичных локальных данных
1.9.9a с явно тестовым revision `aaaa…`; личные списки/конфиг компьютера в VM
не передавались. Для миграции использовался искусственный набор с IPv4/IPv6 из
документационных диапазонов. Сетевое обновление GitHub и фактический обход DPI,
видео/голос/QUIC этим прогоном не подтверждались. Перезагрузка и интерактивный
polkit-диалог новой операции не проверялись.

Повторять сценарий можно только root в отмеченном одноразовом госте с hostname
`zapret-integration` и маркером `/var/tmp/zapret-vm-provisioned`:

```sh
sudo python3 ci/vm_ipset_smoke.py --source /home/vmtest/checkout \
  --acknowledge-disposable-vm
```

Source должен содержать публичные данные/движок/ALT12, тестовый legacy-конфиг,
основной IPSet-заглушку и валидный тестовый `user-lists/ipset-all.txt.backup`.
Сценарий меняет гостевой systemd/firewall и не предназначен для рабочей машины.

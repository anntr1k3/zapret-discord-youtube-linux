# Обновление списка IPSet из GUI

Строка 8 матрицы `service.bat` — «Update IPSet List». В Linux-версии это
отдельная кнопка **«Обновить список IPSet…»** на вкладке **«Настройки»**.
Она не связана с режимами loaded/none/any и с синхронизацией стратегий:
скачивается только основной набор IP/CIDR, конфиг и остальные списки не
переписываются.

## Источник и загрузка

Адрес зафиксирован в `src/lib/strategy_sync.py`, подставить произвольный URL
из окна или через помощник нельзя:

```text
https://raw.githubusercontent.com/Flowseal/zapret-discord-youtube/refs/heads/main/.service/ipset-service.txt
```

Скачивание выполняет обычный непривилегированный процесс GUI. Разрешены только
этот HTTPS-хост и путь внутри репозитория Flowseal; другие схемы, query,
fragment, `..` и посторонние redirect отклоняются. Файл сначала пишется
атомарно в пользовательский кэш
(`~/.cache/zapret-strategy-sync/ipset-service.txt`) с режимом `0600` и только
после этого проверяется тем же инспектором, что и режимы IPSet:

- только литеральные IPv4/IPv6 и числовые CIDR;
- лимиты 8 MiB и 200000 записей;
- пустой список, набор из одной заглушки `203.0.113.113/32` и повреждённые
  строки не считаются загруженным набором;
- повторно вычисляются число записей и SHA-256.

До подтверждения установленная копия, конфиг, firewall и сервис не меняются.
Сеть опрашивается только по нажатию кнопки; фоновой загрузки нет.

## Подтверждение и применение

После успешной проверки окно показывает источник, размер, число записей,
SHA-256 и предлагает подтвердить замену. Отмена оставляет систему как есть.
Подтверждённый запрос уходит установленному root-помощнику через `pkexec` и
содержит только:

```json
{"stage": "/home/…/.cache/zapret-strategy-sync/ipset-service.txt",
 "sha256": "…", "expected_sha256": "…"}
```

`expected_sha256` — токен ранее прочитанного конфига. Помощник принимает stage
только как абсолютный путь к обычному файлу (не symlink), принадлежащему
не-root пользователю, с режимом `0600`; повторно проверяет SHA-256 уже после
чтения. Файл с чужим содержимым, изменённый после просмотра, root-owned stage,
неверный токен и несовместимый формат отклоняются до остановки сервиса.

Транзакция:

1. Проверяет capability `ipset-update-v1`, неизменность конфига и данных stage.
2. Сравнивает новые байты с постоянным
   `/etc/zapret-discord-youtube/user-lists/ipset-all.txt`.
3. Если байты совпадают, ничего не пишет и не перезапускает сервис.
4. Иначе останавливает только активный сервис, атомарно заменяет основной
   пользовательский список (права и владелец сохраняются) и запускает сервис
   обратно, если он работал.
5. При ошибке запуска или записи восстанавливает прежний файл (включая случай,
   когда его не было) и прежнее состояние сервиса. Сбой восстановления
   показывается отдельной ошибкой.

Конфиг (`conf.env`), выбранный режим IPSet, пользовательские исключения,
`ipset-loaded.txt` и остальные списки не изменяются. Релиз в `/opt` не
модифицируется. Остановленный сервис после обновления не запускается.

Если установленный помощник старше этой функции, кнопка отключается с
объяснением; скрытого обновления приложения нет.

## Проверки

16 отдельных офлайн-тестов (`ci/test_ipset_update.py`) покрывают фиксированный
URL и отклонение посторонних адресов, атомарную запись stage с режимом `0600`,
повторную валидацию, заглушку/пустой/повреждённый список, capability, запись с
перезапуском и сохранением прав, отсутствие перезапуска при идентичных байтах,
устаревшие токены и дрейф SHA-256, изменённый после просмотра stage,
symlink/относительный/слишком длинный путь, восстановление при неудачном
запуске (включая отсутствовавший файл) и отказ при изменённом конфиге.

Полный офлайн-набор — **186 тестов**, GTK demo smoke — **18 операций**, включая
имитацию загрузки и применения IPSet.

## Проверка в VM 12 ноября 2026

Отдельная одноразовая KVM VM: Ubuntu 24.04 x86_64, kernel `6.8.0-147-generic`,
nftables 1.0.9, Python 3.12.3. Сценарий `ci/vm_ipset_update_smoke.py` прошёл
**85 утверждений** и напечатал:

```text
IPSET UPDATE VM TEST PASSED (polkit dialog and real DPI bypass not tested)
```

Реальная загрузка (как пользователь `vmtest`, не root) вернула 33336 записей,
543904 байта, SHA-256
`3cc04a2921ab490134c68b6609612f49ca7f69524ad3ddd4c144afc6c3e6ca59`.
Stage был обычным файлом пользователя с режимом `0600`; установленные данные при
скачивании не затрагивались.

В VM проверены: capability установленного помощника; отклонение устаревшего
токена, неверного SHA-256, заглушки, пустого списка, symlink, root-owned stage,
изменения stage после просмотра и параллельной правки конфига с сохранением
чужих байтов; установка неактивного списка без запуска сервиса и без изменения
конфига/прочих списков/релиза; no-op без перезаписи inode; применение при
работающем сервисе с фактическим `--ipset=/etc/zapret-discord-youtube/user-lists/ipset-all.txt`
в `/proc/.../cmdline` настоящего nfqws и сохранением `--ipset-exclude-user.txt`;
перезапуск только при изменении байтов; одноразовый сбой запуска с
восстановлением прежнего списка и работы сервиса; повторное успешное применение;
удаление управляемой установки с сохранением обновлённого списка. Посторонний
nfqws на другой очереди и посторонняя nftables-таблица не пострадали.

Ограничения: интерактивный polkit-диалог и полный путь GUI → pkexec → помощник
в VM не проверялись (помощник вызывался напрямую от root); эффективность обхода
DPI, видео/голос/QUIC и перезагрузка не проверялись. Успешный HTTP-ответ и
валидный список сами по себе не доказывают обход у провайдера. Журнал и
evidence — временные файлы `/tmp/opencode/zapret-ipset-vm/ipset-update.log` и
`ipset-update-result.json`, в репозиторий не входят.

Повторять только root в отмеченном одноразовом госте с hostname
`zapret-integration` и маркером `/var/tmp/zapret-vm-provisioned`:

```sh
sudo python3 ci/vm_ipset_update_smoke.py --source /home/vmtest/checkout \
  --acknowledge-disposable-vm
```

Сценарий меняет гостевой systemd/firewall и не предназначен для рабочей машины.

# Тестировщик стратегий (строка 12): текущее состояние

Вкладка **«Тестировщик»** переносит часть логики эталонного
[`test zapret.ps1`](https://github.com/Flowseal/zapret-discord-youtube/blob/176f56dc3f11ce5915c26abcdde903f93d835b64/utils/test%20zapret.ps1)
(Flowseal 1.10.4) на Linux: типы проб, цели из `utils/targets.txt`,
три варианта TLS и ping, аналитика и рекомендация. Полного паритета пока нет.

Реализован **инкремент 1**: пробы, классификация, аналитика, экспорт и GUI
без административных изменений. В **инкременте 2** реализованы потоковый
протокол помощника, isolated runtime, guarded-транзакция сервиса с cgroup-фильтром
и непривилегированный клиентский runner (`strategy_test_client.py`), подключённый
к GUI через маркер `strategy-tester-v1`. Запуск выбранных стратегий из рабочего
интерфейса подключён.

## Типы тестов

- **Стандартный** — для каждой цели-URL три пробы `curl` (`--http1.1`,
  `--tlsv1.2 --tls-max 1.2`, `--tlsv1.3 --tls-max 1.3`) с `-I`, коротким
  таймаутом и чтением кода ответа, плюс `ping -c 3 -w 10` хоста. Ping-only
  цели проверяются одним ping. Инфраструктурные цели берутся из
   `utils/targets.txt`; при отсутствии, ошибке чтения, превышении размера или
   отсутствии распознанных строк используется встроенный список из 17 целей
   эталона. Недопустимые распознанные цели отклоняются; полностью недопустимый
   список не заменяется молча. Лимит — 64 цели, повторный ключ заменяет прежний.
   Проблемы перечисляются в отчёте.
- **DPI TCP 16–20** — POST с `--data-binary` и `--range 0-65535` на один host:
  либо собственный host из поля ввода, либо цели публичного набора
  `suite.v2.json` с `hyperion-cs.github.io`. Набор скачивается только по
  нажатию «Запустить», проверяется по строгим правилам (допустимый host,
   лимит 64 цели), в экспорт добавляется строка лицензии Apache-2.0.
   Для целей набора разрешаются только глобально маршрутизируемые DNS-адреса:
   private/loopback/link-local и смешанные ответы отклоняются. Curl получает
   закреплённый адрес через `--resolve` с сохранением TLS-имени, без proxy и
   переходов по redirect. Собственный host — явно указанный пользователем;
   публичный набор в этом случае не скачивается.
  Временный файл данных создаётся в системном временном каталоге и удаляется
  после прогона (в том числе при ошибке и отмене).

Запросы выполняются от обычного пользователя с фиксированными аргументами,
без `-k/--insecure` и без изменения TLS-проверки; `-q` первым аргументом curl
отключает чтение пользовательского `.curlrc`. TLS-код ответа не
подделывается: `SSL` с причиной `certificate` показывается как есть.

## Baseline и стратегии

- **Baseline** (стратегии не выбраны) — пробы без изменений сервиса,
  firewall и настроек; root и авторизация не нужны. Это замер текущего
  соединения: уже работающий zapret или другой обход остаётся включённым.
  Результат не является гарантированно чистым замером без nfqws.
- **Выбранные стратегии** — требуется установленный доверенный помощник
  с возможностью `strategy-tester-v1`. Она появится в следующем инкременте:
  помощник остановит текущий сервис, применит каждую стратегию по очереди,
  передаст управление непривилегированным пробам и восстановит прежнее
  состояние с явным сообщением о возможной ошибке восстановления. Это
  требование следующего инкремента, а не проверенное поведение root-помощника.
  Сейчас действие отклоняется даже при обнаружении нового маркера помощника:
  без runner выбранные стратегии не выдаются за действительно запущенные.

## Классификация и аналитика

Стандартные пробы: `OK` (код ответа записан), `SSL` (причины `dns` —
«Could not resolve host», как в эталоне, или `certificate`), `UNSUP`
(не поддерживается клиентом/движком), `ERROR` (остальное). Ping: `OK` со
средним временем или `TIMEOUT`. DPI: `OK` (есть ответ), `LIKELY_BLOCKED`
(данные отправлены, ответа нет, время вышло — рекомендательный признак,
не доказательство), `FAIL`, `UNSUPPORTED`.

Аналитика по каждой стратегии считает категории; **лучшая стратегия**
выбирается по сумме успешных проб, при равенстве — по успешным ping,
затем по меньшему числу `LIKELY_BLOCKED`, при полном равенстве побеждает
ранняя в списке. Отменённый прогон не получает рекомендацию.
Рекомендация **информационная**: профиль применяется
только вручную на вкладке «Сервис», подтверждением и автосохранения нет.
HTTP 200 и успешный ping не доказывают воспроизведение видео, работу QUIC
или голоса Discord.

## Прогресс, отмена, восстановление

Во время прогона показывается шаг (какая стратегия, сколько целей).
Кнопка **«Прервать тест»** расположена вне блокируемых вкладок и остаётся
доступной, пока окно заблокировано операцией: отменённые стратегии
помечаются `CANCELLED`, текущие пробы завершаются, новые не запускаются.
В демо и тестах runner восстановление вызывается ровно один раз после
успешного snapshot, и только после завершения потоков проб. Ошибка остановки тестового
движка или восстановления не скрывается: они попадают в предупреждения
и отдельное поле `restore_error` отчёта.

## Экспорт

Кнопка «Экспорт текстового отчёта…» сохраняет тот же текст, что показан
в окне: через временный файл и атомарную замену, права `0600`; каталог и
symlink отклоняются, прежний файл при сбое не повреждается. Автоматической
записи на диск нет — только явный выбор пути пользователем.

## Инкремент 2: контроллер сеанса (ещё не root-возможность)

После снимка `1b3d2af` добавлен внутренний модуль
`src/lib/strategy_test_session.py`. Он **не подключён** к административным
действиям и не объявляет `strategy-tester-v1`: команды сервиса, запуск nfqws
и изменение firewall этим модулем не выполняются.

Выбран один длительно живущий процесс помощника с одним pipe-каналом,
а не независимые вызовы pkexec для каждого start/stop. Контроллер:

- принимает только список 1–64 уникальных имён стратегий и SHA-256
  прочитанного конфига; пути, argv и произвольные поля не принимаются;
- держит `runtime.operation()` от snapshot до завершения восстановления;
- принимает только `start` из первоначального выбора, `stop`, `restore`;
- при EOF, ошибке канала, таймауте или частично неудачном запуске пытается
  остановить тестовую стратегию и восстановить сохранённое состояние;
- различает ошибку прогона, ошибку очистки и ошибку восстановления;
  успешный вызов restore не скрывает прежнюю ошибку очистки;
- ограничивает число команд (129), паузу между командами (300 секунд),
  общий срок сеанса (3600 секунд) и размер каждого сообщения (16 KiB);
- использует неблокирующие pipe-дескрипторы с deadline для чтения и записи:
  заполненный stdout не должен удерживать путь восстановления;
- отклоняет обрезанный JSON, повторные ключи и не-JSON константы.

**21 офлайн-тест** (`ci/test_strategy_test_session.py`) проверяет эти
свойства на подменном runtime и настоящих локальных pipe, включая busy-lock,
ошибку snapshot, частичные enter/start, KeyboardInterrupt, EOF, неполный
пакет, неизвестную/несогласованную команду и переполнение выходного канала.
Это не проверка polkit или действительного восстановления сервиса.

Проверка выбранных стратегий и изолированный nftables-запуск добавлены
следующим шагом ниже. 16 ноября добавлены проверка очередей и guarded-транзакция
исходного сервиса; подробности и границы VM-проверки — в последнем разделе.
Обработчики SIGTERM/SIGINT и установленная streaming-точка входа также
добавлены и проверены ниже. Ещё нужна интеграция канала с GUI; возможность
GUI runner не объявляется до проверки клиентской стороны.
SIGKILL, сбой ядра и отключение питания не перехватываются `finally`;
аварийное восстановление требует отдельного решения и проверки.

### Installed preflight и изолированный запуск nftables

Внутренний `src/lib/strategy_test_runtime.py` пока не опубликован как
root-действие. Он вызывается только из доверенного установленного кода под
блокировкой установщика (в VM — тестовым сценарием). Нет запуска кода checkout
из рабочего GUI с повышенными правами.

Перед любым изменением состояния `prepare()`:

1. Проверяет управляемый релиз, ревизию конфига и наличие всех выбранных
   стратегий. Неподдерживаемый backend (пока разрешены auto/nftables)
   отклоняется без изменения настроек.
2. Разбирает сырые `.bat` тем же строгим data-only компилятором, что и
   синхронизация; Windows-команды не выполняются. Custom имеет приоритет.
   Каталог `strategies.json` перепроверяется, глобальные параметры вроде
   daemon/pidfile/queue не допускаются в профилях.
3. Материализует Game Filter, установленные списки и активные fakes с
   **IPSet any только в памяти**. Временный конфиг оказался не нужен:
   рабочие файлы вообще не перезаписываются, даже с последующим откатом.
4. Проверяет все планы установленным `nfqws --dry-run`, каждый с таймаутом
   20 секунд и фиксированным окружением без `LD_PRELOAD`/shell. Любой отказ
   завершает подготовку до остановки сервиса.

`IsolatedNftRun` использует foreground child через сохранённый `Popen`,
отдельную очередь (не 220) и случайную таблицу `zapret_test_<id>`. Это ещё
внутренний примитив. В снимке от 13 ноября проверялась только уже занятая
NFQUEUE; 16 ноября добавлены выбор по nft/legacy правилам и повторная
проверка перед запуском. Выбор номера сам по себе не является резервированием
в ядре: nfqws всё равно обязан успешно привязать очередь.

Таблица создаётся одним nft-транзакционным batch через **create**, не add:
совпадение имени с существующей таблицей не даёт права её очищать. Перед
удалением проверяются маркер владения и неизменность JSON-снимка таблицы.
Дрейф приводит к явному отказу удаления; чужое изменение не стирается.
Своя дочерняя программа при этом всё равно останавливается. Применяются
ограниченные ожидания TERM → KILL только для сохранённого child handle;
`pgrep`/`pkill`, старый `service.sh kill` и массовая остановка по exe не
используются. Старый CLI для тестового запуска намеренно не вызван.

**20 офлайн-тестов** (`ci/test_strategy_test_runtime.py`): preflight на
временной offline-установке, stale revision, отсутствие/подмена стратегии,
приоритет custom, строгая проверка каталога, dry-run отказ/таймаут,
неизменность файлов и отсутствие service-команд; отдельный foreground argv,
namespace таблицы, существующая очередь, отказ create, внешний дрейф,
ранний выход child, TERM/KILL и запрет инъекции интерфейса.

### 16 ноября: выбор очереди и транзакция исходного сервиса

`strategy_test_resources.py` собирает занятые номера из привязок NFQUEUE,
всего nft ruleset и загруженных legacy iptables для IPv4/IPv6 (через явно
названные `iptables-legacy-save`/`ip6tables-legacy-save`, не alternatives).
Учитываются одиночные номера, диапазоны и literal sets. Динамические
queue-выражения, непрозрачный compatibility target и недоступный обязательный
инспектор блокируют тестирование. Если legacy-таблицы не загружены, их
чтение не вызывает загрузку модулей. Очереди 0 и 220 не выбираются.

Первичный выбор и повторная проверка перед foreground-запуском происходят
под блокировкой установщика. Это не глобальная kernel-резервация: сторонний
root/CAP_NET_ADMIN не обязан соблюдать блокировку приложения. Эксклюзивная
привязка движка остаётся обязательной; гарантия отсутствия любых гонок с
независимым root-процессом не заявляется.

`strategy_test_service.py` соединяет preflight, allocator и изолированный
child с контроллером сеанса:

- до остановки проверяются исходный профиль (даже если он не выбран для
  теста), config/release, файлы данных, unit и состояние systemd;
- nfqws идентифицируется по исполняемому файлу, PID/starttime, cgroup и
  очереди; ручной процесс с тем же бинарником блокирует начало сеанса;
- существующая таблица приложения проверяется по цепочкам, hook/priority,
  capture-портам, mark, направлениям ct, queue/bypass и комментариям;
  чужая цепочка/правило/эффект не считается собственным ресурсом;
- неизвестное, failed или переходное состояние исходного сервиса отклоняется,
  а не «исправляется» скрытым запуском;
- активный сервис останавливается на время тестов и запускается вновь только
  после подтверждённой очистки своего child/таблицы и проверки отсутствия
  дрейфа. Изначально выключенный сервис не запускается;
- изменение файлов, unit, автозапуска или внешнее переключение сервиса
  приводит к явному отказу автоматических действий. Чужое состояние не
  перезаписывается. Ошибка очистки не маскируется успешным service start.

Исправлена и нижняя граница старого CLI: `stop_nfqws` при systemd-вызове
из управляемой установки (`INVOCATION_ID`) ограничивает сигналы cgroup
управляемого сервиса и её потомками. Это защищает ручной nfqws с тем же
бинарником при ExecStart/ExecStop, а не только при остановке тестового child.
Если cgroup неизвестна, массового fallback нет. Для транзакции требуется
маркер `managed-service-cgroup-stop-v1` в установленном runtime; старый
помощник/релиз не обновляется автоматически. Поведение старого не-systemd
CLI в этом изменении не пересматривается.

# Системная установка: systemd

Установщик `install.py` использует только стандартную библиотеку Python 3.9+.
Сетевых загрузок при установке нет. Он принимает заранее подготовленный и
проверенный checkout с `nfqws`, каталогом стратегий `zapret-latest`, файлами
`src` и выбранной конфигурацией `conf.env`.

**Статус:** файловые операции и ошибки активации проверены офлайн. Запуск,
перезагрузка, обновление, откат и удаление проверены в настоящей KVM VM на
Ubuntu 24.04/nftables — [отчёт](vm-validation-2026-11-09.md). Перед использованием
на рабочем компьютере проверьте своё окружение отдельно: другие дистрибутивы,
iptables и эффективность обхода DPI этим испытанием не покрыты.

## Размещение файлов

| Путь | Назначение |
| --- | --- |
| `/opt/zapret-discord-youtube/releases/<id>` | отдельная версия кода, nfqws и стратегий |
| `/opt/zapret-discord-youtube/current` | атомарно переключаемая ссылка на текущую версию |
| `/etc/zapret-discord-youtube/conf.env` | постоянная конфигурация |
| `/etc/zapret-discord-youtube/user-lists/*.txt` | постоянные пользовательские списки |
| `/var/lib/zapret-discord-youtube/state.json` | текущая и предыдущая версии |
| `/var/lib/zapret-discord-youtube/backups/<id>` | копии конфига и списков перед операциями |
| `/etc/systemd/system/zapret_discord_youtube.service` | управляемый unit |

В настоящей установке файлы создаются от root; разрешение записи группе и
остальным пользователям не допускается. Исходные symlink, FIFO и другие
специальные файлы не принимаются. Биты setuid/setgid и права исходного checkout
не переносятся. Существующие symlink в целевых путях и чужие unit/каталоги
отклоняются, а не перезаписываются. Предполагается, что одновременно эти
каталоги не изменяет другой администратор.

## Подготовка

1. Проверьте код и происхождение бинарника `nfqws`. Установщик не подтверждает
   подлинность загруженных ранее файлов и не заменяет аудит исходной копии.
2. Подготовьте зависимости и стратегии в отдельном checkout. Сам установщик
   ничего не скачивает и не исполняет Bash-скрипты checkout при копировании.
3. Создайте валидный конфиг, например:

   ```ini
   interface=any
   gamefiltertcp=false
   gamefilterudp=false
   strategy=general.bat
   firewall_backend=nftables
   ```

   Указанная стратегия должна существовать. Формат — простой `key=value`,
   без shell-кода и кавычек. Имена интерфейсов и стратегий для установщика — ASCII.
   Резервные `user-lists/*.txt.backup`, созданные старым переключателем ipset,
   остаются в исходной папке. Валидный непустой `ipset-all.txt.backup` сохраняется
   в приватной копии как `ipset-loaded.txt`, если такого файла ещё нет; остальные
   backup не устанавливаются как рабочие списки. Существующие постоянные данные
   при этом не перезаписываются. См. [режимы IPSet](ipset-modes.md).
   Symlink и другие посторонние файлы по-прежнему отклоняются.
4. В VM должны быть Bash, Python, systemd с `systemd-notify`, а также обычные
   зависимости адаптера: git, grep с PCRE, sed, curl, procps и nftables
   (либо iptables + ip6tables).
5. Если уже существует старый unit с тем же именем, сначала отдельно проверьте
   и удалите старую установку. Автоматического захвата чужого/старого unit нет.

## Установка в VM

Из проверенного checkout:

```sh
sudo python3 install.py install --source "$PWD"
```

По умолчанию установщик **не включает автозапуск и не запускает обход**.
После проверки файлов можно включить сервис вручную:

```sh
sudo systemctl enable --now zapret_discord_youtube.service
```

Либо для первоначальной установки явно запросить оба действия:

```sh
sudo python3 install.py install --source "$PWD" --start
```

Unit использует `Type=notify`: готовность отправляется после настройки firewall
и запуска `nfqws`. Это проверка инициализации, а **не доказательство доступности
YouTube/Discord**. Все процессы сервиса управляются общей systemd cgroup.

## Обновление и откат

Подготовьте следующую проверенную копию кода и зависимостей отдельно, затем:

```sh
sudo python3 install.py update --source /absolute/path/to/prepared-checkout
sudo python3 install.py rollback
```

Обновление сначала копируется в новую версию. Активный сервис останавливается
старым кодом **до** переключения ссылки, после чего запускается новым.
Если сервис был неактивен, обновление само его не запускает. Состояние
автозапуска сохраняется. При ошибке активации установщик пытается восстановить
прежние код, unit и состояние сервиса; ошибка повторного запуска старой версии
выводится явно и требует ручного вмешательства.

Перед восстановительным запуском сбрасывается состояние failed и счётчик
ограничения частых стартов этого unit (`systemctl reset-failed`). Иначе systemd
может запретить запуск исправной версии после ошибки кандидата. Сам лимит
частых перезапусков не отключается.

При отмене первоначальной установки попытка включения автозапуска отменяется
до удаления файла unit: иначе systemd не сможет корректно удалить его ссылки.

Конфиг и существующие пользовательские списки не перезаписываются данными из
checkout. Резервные копии находятся в `backups`. `rollback` переключает код на
предыдущую версию, но **сохраняет актуальные настройки и списки**. Если текущая
конфигурация несовместима с предыдущей версией (например, стратегия отсутствует),
откат отклоняется до остановки сервиса. Восстановление конфига из резервной копии
выполняется администратором отдельно, при остановленном сервисе.

Устаревшие версии автоматически не удаляются: следите за местом в `/opt` и
`/var/lib`. Переключение ссылки и отдельные записи файлов атомарны, но вся
операция **не является транзакцией при отключении питания или SIGKILL**. При
расхождении `current` и `state.json` установщик останавливается с ошибкой, не
пытаясь угадывать нужную версию.

## Удаление

```sh
sudo python3 install.py remove
```

Сервис останавливается и отключается, управляемый unit и версии кода удаляются.
Конфиг, списки, резервные копии и служебные каталоги сохраняются. Повторная
установка использует сохранённые данные. Автоматического `purge` нет.

## Управление установленной копией

Используйте `systemctl` для запуска/остановки и `install.py` для установки,
обновления, отката и удаления. В каждой версии сохраняется копия установщика;
например, перед удалением его можно вызвать по пути
`/opt/zapret-discord-youtube/current/install.py`.

Не запускайте в установленной версии старые `service install/remove` и
`download-deps`: они отклоняются, чтобы не нарушить метаданные и откат.
Смена ipset-режима через старое меню отключена; для новой управляемой установки
доступны [режимы IPSet в GUI](ipset-modes.md) без изменения набора на месте. Конфиг и списки
редактируются администратором в `/etc`; перед сменой firewall-бэкенда сначала
остановите сервис. Пользовательские ссылки на файлы списков не поддерживаются.
Стратегии подставляют постоянные `.txt`-списки по совпадающему имени файла.

## Полностью офлайн-проверка без sudo

Существующий пустой каталог можно использовать как корень файлового макета:

```sh
python3 install.py install --root /absolute/path/to/empty-directory --source "$PWD"
python3 install.py update --root /absolute/path/to/empty-directory --source "$PWD"
python3 install.py rollback --root /absolute/path/to/empty-directory
python3 install.py remove --root /absolute/path/to/empty-directory
```

В этом режиме нет вызовов настоящего systemd, chown или запуска `nfqws`.
Не используйте sudo для офлайн-макета; его файлы принадлежат текущему
пользователю, поэтому это не готовая привилегированная установка.
`--start` недоступен. Реальные unit-пути в макете намеренно указывают на `/opt`
и `/etc`: не копируйте его unit в рабочую систему вручную.

Автоматические проверки:

```sh
python3 ci/test_regressions.py
python3 ci/test_installer.py
```

Если доступен `systemd-analyze`, дополнительно выполняется статическая проверка
сгенерированного unit. Другие тесты работают без systemd.

## Что проверить в одноразовой VM

Автоматический гостевой сценарий находится в `ci/vm_smoke.py`. Он требует root,
явного `--acknowledge-disposable-vm`, hostname `zapret-integration` и маркера
`/var/tmp/zapret-vm-provisioned`. Создавайте такой маркер **только внутри
одноразовой VM**, никогда на основной машине. На VM без предыдущей установки,
с подготовленным checkout и конфигом:

```sh
sudo python3 ci/vm_smoke.py install --source "$PWD" --acknowledge-disposable-vm
sudo systemctl reboot
# После повторного подключения к этой же VM:
sudo python3 ci/vm_smoke.py lifecycle --source "$PWD" --acknowledge-disposable-vm
```

Сценарий создаёт и удаляет настоящие сервисы/правила, добавляет тестовую запись
в пользовательский список и намеренно проверяет неудачные запуски. Это не обычный
unit-тест, и он не включён в офлайн-запуск CI. Результаты гостя сохраняются в
`/var/tmp/zapret-vm-smoke`. Полный прогон требует свежей VM, не повторного запуска
поверх оставшихся тестовых каталогов.

Ниже перечислена матрица проверок; результаты выполненного прогона приведены в
отчёте. Последний пункт остаётся отдельной сетевой проверкой.

- Установку без `--start`: сервис не включён и не запущен.
- Запуск и уведомление готовности; остановку без оставшегося `nfqws`.
- Автозапуск после перезагрузки.
- Обновление активного и неактивного сервиса, сохранность `/etc`.
- Ошибку старта кандидата и восстановление прежней версии.
- Явный откат и удаление с сохранением данных.
- Сохранность посторонних nftables/iptables правил и процессов.
- Сетевые сценарии YouTube, QUIC и голосового Discord отдельно от готовности unit.

Для обновления только данных Flowseal теперь есть отдельная
[автосинхронизация с подтверждением](strategy-sync.md). Автоматическое
восстановление после потери питания, установка для других init-систем и
изоляция нескольких экземпляров пока не реализованы.

# Доверенная установка: этап исправления после аудита

## Граница доверия

GUI не повышает права `install.py`, Bash-кода или `nfqws` из пользовательского
checkout. Установка и удаление сервиса используют только постоянный
`/usr/lib/zapret-discord-youtube/src/gui/bootstrap.py` через изолированный Python
и pkexec. Если bootstrap отсутствует или его путь небезопасен, операция
отклоняется до subprocess и без записи локального `conf.env`.

Bootstrap проверяет своё фиксированное размещение, владельца root, отсутствие
групповой/общей записи, symlink и специальных файлов во всём дереве приложения
и его родителях **до загрузки установщика**. Доверенная поставка должна содержать:

- `gui.py`, `sync.py`, `install.py`, `src/` и ресурсы приложения;
- `runtime/` с проверенным движком, адаптером и каталогом стратегий.

Root-owned путь сам по себе не подтверждает происхождение движка. Его проверку
и доставку должен обеспечивать процесс сборки доверенного пакета. Копирование
произвольного пользовательского `nfqws` туда не является решением.
Предполагается отсутствие конкурентных изменений пакета другим администратором.

## Ограниченный протокол

Принимаются только:

```json
{"strategy": "general_alt12.bat", "start": true}
```

для `install-service` и `{"purge": false}` для `remove-service`.
`strategy: null` означает начальный ALT12. Не принимаются пути исходников,
движка, конфигурации, целевого root, команды или дополнительные поля.

Начальная конфигурация генерируется в приватном snapshot внутри операции
установщика. Уже сохранённый `/etc/zapret-discord-youtube/conf.env` не
перезаписывается выбором в диалоге повторной установки. При неудачной начальной
активации новый конфиг удаляется, если восстановление убрало кандидат.
При ошибке восстановления с оставшимся текущим кандидатом конфиг сохраняется.

## Жизненные циклы

- `/usr/lib/zapret-discord-youtube` — постоянное приложение, bootstrap и payload;
- `/opt/zapret-discord-youtube/releases` и `current` — сменные версии сервиса;
- `/etc/zapret-discord-youtube` — данные пользователя;
- `/var/lib/zapret-discord-youtube` — состояние, резервные копии и блокировка.

Удаление сервиса не удаляет `/usr/lib` и по умолчанию сохраняет данные.
Явный purge очищает данные и резервные копии под той же блокировкой. Каталог
состояния с `.managed` и `.install.lock` остаётся: удаление удерживаемого inode
блокировки позволило бы параллельному процессу создать другую блокировку.

## Что ещё не подтверждено

Текущий этап проверен офлайн: запрет checkout-elevation, отмена авторизации
(подмена subprocess), валидация протокола/прав, установка → удаление → повторная
установка и purge с проверкой удерживаемой блокировки. Это не подтверждает
интерактивный polkit, работоспособность опубликованного `.deb`, реальный запуск
движка, firewall или обход DPI.

## Сборка и проверка `.deb`

`scripts/build-deb.sh --output /tmp/opencode/zapret-artifacts` без root собирает
кандидат `1.0.1~rc1` только для `amd64`. Номер Debian выводится из
`src/app-version.json`: GUI показывает `1.0.1-rc1`, `release=false`, а `~` в
Debian сохраняет правильный порядок обновлений (`1.0.0 < 1.0.1~rc1 < 1.0.1`).
Скрипт получает архивы zapret `v72.9` и
Flowseal `1.10.4` (конкретный commit), проверяет закреплённые SHA-256 обоих
архивов и отдельно SHA-256 `nfqws` по контрольной сумме автора. Значения и
имена находятся в `scripts/stage-deb-runtime.py`. Для офлайн-сборки
`--inputs DIRECTORY` принимает те же `zapret-v72.9.tar.gz` и `flowseal.zip` с
теми же проверками. Изменившийся upstream-архив приведёт к отказу: обновлять
пин следует только после независимой проверки происхождения. Сборка не
использует `nfqws`, `zapret-latest`, `conf.env` и `user-lists` из checkout.

Пакет содержит GUI, bootstrap и проверенный runtime, но не unit, `/opt/.../current`
или maintainer scripts. Установка, обновление и удаление **нового** пакета сами
не управляют сервисом. Чтобы удалить оба компонента, сначала удалите сервис
из GUI (или штатным управляемым CLI), затем приложение пакетным менеджером.
Обновление с чистой установки опубликованного `v1.0.0` проверено отдельно. Если
после обновления на месте `current` остаётся чужой каталог, установщик откажется его присваивать.
Не удаляйте такой каталог автоматически; отдельно проверьте содержимое и
сделайте резервную копию. В старом `.deb` есть собственные maintainer scripts:
гарантии нового пакета на них не распространяются.

Проверка готового артефакта без установки:

```sh
ZAPRET_TEST_DEB=/absolute/path/to/zapret-discord-youtube_1.0.1~rc1_amd64.deb \
  python3 -m unittest ci.test_deb
```

Проверка в **чистой одноразовой VM** с hostname `zapret-integration` и
маркером `/var/tmp/zapret-vm-provisioned`:

```sh
sudo python3 ci/vm_deb_smoke.py /absolute/path/to/package.deb --acknowledge-disposable-vm
```

Сценарий устанавливает именно указанный артефакт и проверяет жизненные циклы
с настоящими systemd и nftables. Передайте `--legacy-artifact /path/to/v1.0.0.deb`
для сценария обновления, `--tester` для теста потокового протокола.

На двух отдельных Ubuntu 24.04.5 LTS VM проверен **один и тот же** кандидат
SHA-256 `0687d4b5a8b65e40603783c93c795f698afd6088d5fabc5351c6a6fc2bf0e637`.
Пройдены свежая установка и обновление с чистого GitHub Release `v1.0.0`,
запуск `nfqws`, install → remove → reinstall с сохранением ALT12 и списков,
отдельное удаление приложения, purge с сохранением bootstrap и 34 операции
GTK demo из установленного пакета без root. Установленный CLI из `/` нашёл
профиль и прошёл остановку с очисткой nftables и повторный запуск.

В обоих прогонах `--tester` использовал реальные pipe, nftables и `nfqws`.
Исходное состояние активного и неактивного сервиса восстановлено; при
имитации таймаута подтверждения запуска клиент прекратил тест, а помощник
очистил временную таблицу и восстановил сервис. Дополнительно пройдены
536 офлайн-тестов и 88 dry-run для 22 профилей из того же пакета.

Это не подтверждает миграцию вручную изменённой установки, другие
дистрибутивы или качество обхода Discord/YouTube.
`.github/workflows/test-strategies.yml` теперь собирает пакет без root,
проверяет его и запускает системные операции только на отмеченной одноразовой
GitHub-hosted VM. Новый workflow ещё не запускался на GitHub.

`vm_deb_smoke.py` запускает bootstrap непосредственно от root. В отдельной
Ubuntu 24.04.5 VM тот же кандидат проверен с настоящим графическим агентом
polkit: непривилегированный backend вызвал `pkexec`, появилось окно
`Authenticate`, и Escape отменил операцию. На чистой установке не появились
unit и конфиг; при сохранённом конфиге его SHA-256 не изменился и unit не
создался.

Следующий прогон того же пакета задействовал **установленное окно Zapret**:
кнопки активировались через AT-SPI в сеансе Xvfb/Openbox, запросы обрабатывал
настоящий GTK-агент polkit. Отмена показала ошибку с подробностями и не
создала ни unit, ни конфиг. Успешная авторизация установила и запустила ALT12;
удаление без purge сохранило конфиг. Повторная отмена после удаления сохранила
его SHA-256 и не восстановила unit, а повторная авторизация вернула сервис
с тем же конфигом. Испытание проводилось в одноразовой Ubuntu 24.04.5 VM,
не в пользовательском сеансе GNOME/Wayland.

Системное действие «Тестировщик стратегий» также прошло проверку: открылась
настоящая вкладка, экспорт отчёта оставался недоступен, диалог polkit и
тестовая nftables-таблица не появились, исходный сервис остался активен.
Итоговый графический прогон завершился с кодом `0` после удаления сервиса.
